# 도리보고 — 카드뉴스형 AI 생태계 조사 MVP

## 프로젝트 이름
**도리보고**

'요리보고 저리보고'처럼 AI 생태계를 여기저기 살펴보고, 여러 곳에서 발견한 서로 다른 이슈와 반응을 한눈에 보여준다.

## 목적
X, Threads, Reddit, GitHub와 한국 커뮤니티/서비스 등에서 최근 AI 관련 움직임을 조사한다. 대상 자체를 길게 설명하는 것이 아니라, **그 대상에서 최근 실제로 벌어지고 있는 서로 다른 이슈를 찾아 카드별로 정리**하는 것이 핵심이다.

## 사용 방식
사용자가 조사할 대상/주제와 원하는 카드 수를 지정한다.

예:
- `OpenCode Go 최근 이슈 5개`
- `이번 주 AI Agent 이슈 10개`
- `Codex 최근 이슈 7개`

대상에 대한 기본 설명은 짧게 끝낸다. 이후 요청한 개수만큼 **서로 다른 의미를 가진 최근 이슈**를 찾는다.

카드 수를 채우기 위해 비슷한 내용을 억지로 나누거나 중요도가 낮은 내용을 만들어내지 않는다. 요청 개수보다 의미 있는 이슈가 적다면 그 사실을 명확히 알린다.

## 검색 소스
기본 후보 소스는 다음 10곳이다.

### 글로벌
1. X
2. Threads
3. Reddit
4. GitHub

### 한국
5. GeekNews
6. OKKY
7. GPTers
8. 디스콰이엇
9. Velog
10. AI Hub

주제에 따라 모든 소스를 기계적으로 검색하지 않는다. 이슈와 관련성이 높은 소스를 우선 확인하고, 필요하면 뉴스·논문·공식 문서 등 추가 출처로 교차검증한다.

## 핵심 조사 방식
1. 대상이 무엇인지 초보자도 이해할 수 있도록 짧게 설명한다.
2. 여러 소스에서 최근 자료를 찾는다.
3. 같은 사건/주제/흐름을 하나의 이슈로 묶는다.
4. 서로 다른 이슈는 서로 다른 카드로 분리한다.
5. 각 이슈가 무엇인지 먼저 설명한다.
6. 왜 이런 일이 생겼는지, 왜 중요한지 등 이해에 필요한 배경을 설명한다.
7. 그 이슈에 대해 실제로 의견이나 경험이 확인되는 사이트만 골라 한줄평으로 정리한다.
8. 작성자와 원문 URL을 가능한 경우 기록한다.
9. 사실, 작성자의 주장, 도리보고의 해석을 구분한다.
10. 실제 프로젝트/사용 사례가 있는지 확인한다.
11. 신호 강도를 평가한다.

## 카드 구성 원칙
카드의 틀은 유지하되 모든 카드가 똑같은 문장을 반복하지 않는다. **이슈의 성격에 맞춰 설명 항목을 유연하게 구성한다.**

기본 흐름:

1. `CARD NN` + 이슈 제목
2. `💡 이게 무슨 이슈야?` — 초보자도 이해할 수 있는 설명
3. `🔎 무슨 일이 벌어졌어?` — 최근 발생한 변화/사건/논쟁/문제
4. `❓ 왜 중요한데?` — 필요한 경우 배경과 의미
5. `📌 확인된 사실` — 확인 가능한 정보
6. `🌐 사이트별 한줄평` — 해당 이슈에 실제 의견이 있는 출처만 표시
7. `⚠️ 주의할 점 / 아직 모르는 것` — 단정할 수 없는 부분
8. `👤 작성자 / 원문` — 가능한 경우
9. `🔥 신호` — 강도 평가

이슈에 따라 `실제 사용 사례`, `버그가 발생한 환경`, `새 기능의 변화`, `가격/정책 변경` 등 필요한 설명을 추가할 수 있다.

## 사이트별 한줄평
한줄평은 **이슈 설명 아래에 배치한다.** 한줄평만 보고 독자가 이슈를 추측하게 만들지 않는다.

예:

```text
## 🟥 CARD 03 — ⚠️ 사용량 제한 논쟁

### "$10인데 생각보다 빨리 제한된다는 말이 나온다"

💡 이게 무슨 이슈야?
OpenCode Go는 여러 AI 모델을 월정액으로 사용할 수 있지만,
원하는 만큼 무제한으로 사용할 수 있는 API와는 다른 구조다.

🔎 무슨 일이 벌어졌어?
일부 사용자가 예상보다 빠르게 사용 한도에 도달했다고 보고하면서,
월 $10 구독으로 실제 어느 정도까지 사용할 수 있는지가 논쟁이 되고 있다.

❓ 왜 중요한데?
AI 코딩 Agent는 한 번의 작업에서도 모델을 여러 번 호출할 수 있어
작업량이 많은 사용자는 일반적인 채팅보다 사용량이 빠르게 늘어날 수 있다.

📌 확인된 사실
일부 사용자의 제한 관련 사례가 확인됐다.

🌐 사이트별 한줄평
- Reddit — 실제 사용량에 따라 한도가 빨리 소진될 수 있다는 경험담.
- GitHub — 사용 한도와 계산 방식에 대한 문제 제기.
- X — 가격은 매력적이지만 많이 사용하는 사람에게 제한이 아쉽다는 반응.

⚠️ 주의할 점
일부 사용자 사례를 근거로 모든 사용자가 빨리 제한된다고 단정하지 않는다.
사용 모델과 작업량에 따라 체감 사용량은 달라질 수 있다.
```

모든 사이트에 억지로 한줄평을 만들지 않는다. 해당 이슈에 대한 실제 의견을 찾지 못한 사이트는 생략한다.

## 반응 분석
반응은 필요에 따라 다음과 같이 분류한다.

- 긍정
- 중립/관심
- 부정/비판
- 실제 사용 경험
- 실제 프로젝트/구현

단순 언급량만으로 신호 강도를 결정하지 않는다. 여러 독립 출처에서 반복되는지, 실제 사용/프로젝트로 이어졌는지, 최근에 발생한 변화인지 등을 함께 본다.

## 글쓰기 원칙
도리보고의 글은 **초보 개발자도 읽고 바로 이해할 수 있어야 한다.** 전문용어를 없애는 것이 아니라, 처음 나왔을 때 쉬운 말로 풀어준다.

저장소의 **`IM_NOT_AI` 규칙을 글쓰기 기준으로 참고하고 준수한다.** 해당 규칙 파일 자체를 도리보고가 임의로 수정하지 않는다.

- 번역투와 딱딱한 문장을 피한다.
- 사람이 실제로 설명하는 것처럼 자연스럽게 쓴다.
- 자료를 나열하지 말고 흐름이 이어지게 설명한다.
- `사실`과 `작성자의 주장`과 `도리보고의 해석`을 섞지 않는다.
- 어려운 용어는 필요한 만큼만 사용하고 쉽게 풀어준다.
- 의미 없는 상투적 표현을 반복하지 않는다.

## 데이터 저장 원칙
- GitHub에는 코드, 설계, 규칙만 저장한다.
- 검색할 때마다 원문 데이터를 GitHub에 누적하지 않는다.
- 이미지/스크린샷/원문 대량 저장을 하지 않는다.
- 조사 결과는 기본적으로 대화에서 보여주며, 장기 보관이 필요할 때만 별도 저장을 검토한다.

## MVP 단계
- 웹/API 자동 수집은 아직 넣지 않는다.
- ChatGPT가 실제 웹 검색으로 자료를 찾고 카드 형식으로 정리하는 방식을 먼저 검증한다.
- 실제 사용을 반복하면서 카드 구조와 평가 기준을 다듬는다.
- 그 다음 자동 수집/API 연동 여부를 결정한다.
