# 🛰️ 도리보고 (Doribogo)

> 요리보고 저리보고, **도리보고!**

AI 생태계에서 최근 무슨 일이 벌어지고 있는지 여러 곳을 돌아다니며 찾아보고, 서로 다른 이슈를 카드별로 정리한 뒤 관련 사이트의 반응까지 한눈에 보여주는 조사 프로젝트다.

단순한 뉴스 요약기가 아니다.

**주제 자체의 설명은 짧게 끝내고, 그 주제 안에서 최근 실제로 벌어진 서로 다른 변화·사건·논쟁·문제를 찾아내는 것**이 핵심이다.

---

## 📁 프로젝트 위치

이 프로젝트는 `hodori_gjc` 저장소의 아래 폴더에서 관리한다.

```text
chatgpt-workspace/
└── doribogo/
    └── README.md
```

`chatgpt-workspace`는 ChatGPT와 호도리가 함께 아이디어를 검증하고 작은 실험을 진행하는 작업 공간이다.

현재 도리보고는 **코드를 크게 만드는 단계가 아니라 조사 방식과 결과 형식을 검증하는 MVP 단계**다.

# 🎯 도리보고가 하는 일

도리보고는 크게 두 가지 방식으로 사용할 수 있다.

## DRT — 요리조리 보고와라!

**Dori + Topic**

사용자가 특정 주제를 정해주면 그 대상을 요리조리 살펴본다.

예:

```text
DRT
주제: OpenCode Go
개수: 5
기간: 최근 7일
```

결과는 다음과 같은 흐름이다.

```text
주제 입력
  ↓
대상에 대한 짧은 설명
  ↓
여러 소스 조사
  ↓
최근 이슈 발견
  ↓
서로 다른 이슈끼리 분리
  ↓
각 이슈를 다시 깊게 확인
  ↓
반응과 맥락 확인
  ↓
도리보고 카드 생성
```

## DRI — 이슈보고 저리보고!

**Dori + Issue**

특정 대상을 정하지 않고, 도리보고가 여러 소스를 돌아다니며 최근 이슈를 찾아온다.

예:

```text
DRI
분야: AI
개수: 5
기간: 오늘
```

흐름은 다음과 같다.

```text
여러 소스 탐색
  ↓
최근 자료 수집
  ↓
사람들이 실제로 관심을 보이는 신호 확인
  ↓
비슷한 자료끼리 묶기
  ↓
하나의 이슈인지 판단
  ↓
이슈 후보 우선순위 결정
  ↓
각 이슈를 다시 깊게 조사
  ↓
카드 생성
```

### 두 모드의 차이

| 모드 | 역할 |
|---|---|
| **DRT** | 내가 주제를 준다 → 도리보고가 조사한다 |
| **DRI** | 주제를 정하지 않는다 → 도리보고가 이슈를 찾아온다 |

중요한 것은 검색한 사이트의 숫자가 아니라, **서로 다른 곳에서 실제로 같은 이슈가 확인되는지**다.

# 🎯 어떤 이슈를 가져올 것인가?

DRI의 핵심은 **"AI와 관련된 최신 글을 많이 가져오는 것"이 아니다.**

사람들이 실제로 멈춰서 읽거나, 써보거나, 공유하거나, 의견을 나눌 만한 **관심 포인트가 있는 이슈**를 골라내는 것이 목적이다.

최근 AI 관련 게시물을 조사하면서 `unclejobs.ai`, `choi.openai`처럼 영향력 있는 계정의 콘텐츠가 단순한 뉴스 나열보다 **새로운 변화 + 실제 사용 맥락 + 숫자/사례 + "그래서 뭐가 달라지는데?"라는 관점**을 중심으로 구성되는 점을 참고한다. 예를 들어 unclejobs.ai의 한 게시물은 여러 모델의 성능 변화만 나열하지 않고, 실제 코딩 도구에서 어떻게 활용하는지와 하이브리드 사용 방식까지 하나의 흐름으로 묶었다.

따라서 도리보고는 다음 신호를 함께 본다.

### 🔥 1. 실제 변화가 있는가?
새 모델 출시, 가격 변경, 사용량 변경, 기능 추가, 정책 변경, 서비스 장애처럼 **실제로 무언가가 바뀐 사건**을 우선한다.

### 👀 2. 사람들이 실제로 반응하고 있는가?
좋아요·댓글·공유 같은 단순 숫자만 보지 않는다. 여러 사람이 자신의 경험을 남기거나 같은 문제를 이야기하는지 확인한다.

Threads 데이터 분석 서비스처럼 바이럴 게시물만 보는 것이 아니라 최근 게시물량과 키워드 추세도 관심도를 판단하는 참고 신호로 사용할 수 있다.

### 🧪 3. 직접 써볼 수 있는 변화인가?
새 기능이나 모델이 실제 개발·자동화·업무에 바로 적용될 수 있다면 우선순위를 높인다.

### 💰 4. 돈이나 사용량에 영향을 주는가?
가격, 무료 한도, 토큰 사용량, API 비용, GPU 비용처럼 **사용자가 실제로 체감할 수 있는 변화**는 중요한 이슈 신호다.

### 🧩 5. 기존 방식이 바뀌는가?
단순한 신제품 소개보다 **기존에 하던 일을 다른 방식으로 하게 만드는 변화**를 중요하게 본다. 예를 들어 AI 코딩 도구에서 모델 자체뿐 아니라 하네스·검증·제품화 방식이 중요해지는 흐름처럼, 사용 방식의 변화가 있으면 별도 이슈로 본다.

### 🗣️ 6. 의견이 갈리는가?
사람마다 평가가 다르거나 논쟁이 붙는 주제는 관심도가 높을 가능성이 있다. 다만 논쟁 자체를 사실로 취급하지 않고 원자료를 다시 확인한다.

### 📈 7. 하나의 게시물보다 큰 흐름인가?
한 계정의 글 하나만 보고 이슈로 확정하지 않는다. 가능하면 다른 커뮤니티·뉴스·공식 자료에서도 같은 현상이 확인되는지 본다.

### 🧠 8. "그래서 뭐가 달라지는데?"에 답할 수 있는가?
이 질문에 답할 수 없는 단순 발표·홍보성 내용은 우선순위를 낮춘다.

# 🐙 GitHub 발견 레이더 — DRI에서 항상 하나는 찾는다

AI 개발 생태계에서는 새 저장소가 만들어지는 것뿐 아니라 **기존 프로젝트가 갑자기 주목받거나 대형 업데이트로 다시 뜨는 경우**가 많다.

따라서 DRI를 실행할 때는 일반 AI 이슈와 별도로 **GitHub에서 최근 움직임이 큰 프로젝트를 최소 1개 이상 확인한다.**

### 무엇을 찾나?

```text
🆕 새로 등장한 프로젝트
+
🚀 최근 급상승한 기존 프로젝트
+
🔥 대형 업데이트가 나온 프로젝트
```

### GitHub 프로젝트 선정 신호

- 최근 Star 증가가 눈에 띄는가?
- GitHub Trending 또는 커뮤니티에서 갑자기 등장했는가?
- 최근 커밋·릴리스·업데이트가 활발한가?
- 실제로 설치하고 시험할 수 있는가?
- Agent / Coding Agent / MCP / Skills / Memory / Harness / Orchestration / Local AI / Automation 등 현재 AI 개발 흐름과 연결되는가?
- 기존 문제를 새로운 방식으로 해결하는가?
- 유명 개발자·기업·커뮤니티에서 갑자기 언급되기 시작했는가?
- **호도리가 직접 실험해볼 가치가 있는가?**

### 중요한 원칙

**"새 저장소"만 찾는 것이 아니다.**

이미 존재하던 프로젝트가 최근 며칠 사이 갑자기 뜨기 시작했다면 그것도 좋은 발견이다.

반대로 Star가 많다는 이유만으로 넣지 않는다. 오래된 인기 저장소보다 **지금 실제로 움직이고 있고, 왜 갑자기 관심을 받는지 설명할 수 있는 프로젝트**를 우선한다.

### DRI 결과에서의 위치

요청한 이슈 개수가 3개라면 기본적으로 다음과 같이 구성할 수 있다.

```text
CARD 01 → AI 생태계 주요 이슈
CARD 02 → 개발자들이 실제로 반응하는 이슈
CARD 03 → 🐙 GitHub에서 지금 뜨는 프로젝트
```

단, GitHub에서 정말 의미 있는 후보가 발견되지 않은 날에는 억지로 채우지 않는다. **좋은 프로젝트를 발견하는 것이 목적이지 카드 개수를 맞추는 것이 목적이 아니다.**

GitHub 카드는 단순 저장소 소개가 아니라 다음을 설명한다.

```text
🔥 왜 지금 뜨고 있지?
👀 사람들이 왜 관심을 갖지?
🧩 뭘 해결하는 프로젝트지?
🧪 실제로 뭘 해볼 수 있지?
🐯 호도리가 써볼 가치가 있나?
```

# 🧮 이슈 선별 원칙

도리보고는 **검색 결과가 최신이라는 이유만으로 카드에 넣지 않는다.**

개념적으로 다음 요소를 함께 평가한다.

```text
최근성
+ 관심 신호
+ 실제 변화
+ 실사용 영향
+ 출처 다양성
+ 논쟁성
+ 지속 가능성
= 이슈 우선순위
```

이 숫자를 실제 점수로 고정할 필요는 없다. MVP 단계에서는 조사 과정에서 이 기준을 사용해 사람이 읽을 가치가 높은 이슈를 골라낸다.

**중요:** 조회수나 좋아요가 높다고 무조건 좋은 이슈는 아니다. 반대로 숫자가 작더라도 개발자에게 직접 영향을 주는 가격 변경·보안 문제·치명적인 장애처럼 중요한 이슈는 우선할 수 있다.

---

# 🧩 카드의 핵심 구조

도리보고에서 **카드 하나는 서로 다른 이슈 하나**다.

예를 들어 OpenCode Go를 조사한다면:

```text
CARD 01 → 새로운 모델 추가
CARD 02 → 사용량 급증
CARD 03 → 사용량 제한 논쟁
CARD 04 → 특정 오류 발생
CARD 05 → 가격 대비 가치 논쟁
```

같은 내용을 표현만 바꿔 여러 카드로 만들지 않는다.

사용자가 `5개`를 요청했다고 해서 의미 없는 이슈를 억지로 추가하지도 않는다.

**자료 8개가 발견됐다고 카드 8개를 만드는 것도 아니다.** 비슷한 게시물 여러 개가 하나의 사건을 말한다면 하나의 이슈로 묶는다.

# 📰 카드 작성 방식

기존의 단순한 **"이슈 설명 → 사이트별 한줄평"** 구조에서 한 단계 발전시킨다.

카드는 **뉴스를 전달하는 것이 아니라, 읽는 사람이 이슈를 이해하도록 하나의 흐름을 만드는 것**을 목표로 한다.

```text
## 🟥 CARD 01

🔥 한 줄 핵심
"그래서 지금 무슨 일이 벌어지고 있나?"

👀 지금 무슨 일이야?
짧은 배경과 사건 설명

💡 그래서 뭐가 달라졌는데?
실제 사용자 입장에서 달라진 점

🧩 직접 보면
모델 / 기능 / 수치 / 사례 / 원자료

🤔 왜 이게 중요한데?
도리보고가 여러 자료를 비교해서 설명

🌐 사람들이 왜 반응했어?
실제 반응과 그 이유를 압축

⚠️ 이것만은 조심
확인되지 않은 주장 / 과장 / 표본의 한계

👤 작성자 / 원문
출처와 게시자

🔥 신호
```

### 카드에서 중요한 순서

1. **한 줄 핵심**
2. **무슨 일이 벌어졌는지**
3. **그래서 실제로 뭐가 달라졌는지**
4. **확인할 수 있는 자료·수치·사례**
5. **왜 중요한지**
6. **사람들이 왜 반응하는지**
7. **주의할 점**
8. 작성자와 원문
9. 신호 강도

이슈 성격에 따라 필요한 설명은 달라질 수 있다. 새 모델 출시라면 모델 변화가 중심이고, 버그라면 어떤 환경에서 문제가 발생했는지가 더 중요할 수 있다.

---

# 💬 사이트별 반응은 "근거"로 사용한다

같은 이슈에 대한 사이트별 의견을 카드의 주인공으로 만들지 않는다.

기존 방식:

```text
Reddit — 이런 반응
X — 이런 반응
GitHub — 이런 반응
```

개선된 방식:

```text
🌐 사람들이 왜 반응했어?

AI 코딩 에이전트 사용량이 생각보다 빠르게 늘어난다는
경험담이 여러 곳에서 나오면서 논쟁이 커지고 있다.
```

즉, 여러 사이트의 반응을 **하나의 맥락으로 압축**한다.

# ✏️ 글쓰기 원칙

도리보고 결과는 초보 개발자도 바로 이해할 수 있게 작성한다.

- 전문용어는 처음 나왔을 때 쉬운 말로 설명한다.
- 번역투와 로봇 같은 상투어를 피한다.
- 사실과 작성자의 주장과 도리보고의 해석을 구분한다.
- 출처와 작성자를 확인할 수 있게 한다.
- `IM_NOT_AI.md`의 글쓰기 기준을 참고한다.
- 카드마다 같은 문장 구조를 기계적으로 반복하지 않는다.
- 이슈의 성격에 따라 설명의 깊이와 순서를 바꾼다.

# 📦 자료 보관

도리보고는 검색할 때마다 원문과 이미지 자료를 GitHub에 쌓지 않는다.

현재는 **ChatGPT 웹 검색 → 여러 출처 조사 → 이슈 분류 → 반응 확인 → 카드뉴스형 텍스트 작성** 방식으로 MVP를 검증한다.

GitHub 발견 레이더도 **발견한 저장소 자체를 복사하거나 이미지로 저장하지 않고**, 필요한 정보와 원문 링크만 결과에 남기는 방향을 기본으로 한다.

# 🚧 현재 단계

도리보고는 아직 자동 수집 프로그램을 만드는 단계가 아니다.

현재 목표는 먼저 **"사람들이 실제로 읽고 싶어 하는 이슈를 어떻게 찾고, 어떻게 이해하기 쉽게 보여줄 것인가"**를 검증하는 것이다.
